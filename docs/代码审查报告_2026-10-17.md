## 1. 功能性 Bug（优先修复）

### BUG-1【P0 · 已实测确认】配置路径未随工作区迁移

**位置**：`config.yaml:5`、`~/.workbuddy/mcp.json`

**实测证据**：
```
E:/Workbuddy/离线AI/.offline-bridge/        ← 实际存在的 bridge 目录（inbox/outbox/context/log）
E:/Workbuddy/2026-10-11-17-27-15/           ← config 指向的旧 workspace，已不存在
```

**后果**：
- `mcp.json` 的 `args` 指向 `E:/Workbuddy/2026-10-11-17-27-15/offline-ai/server/mcp_server.py` —— 该文件已不存在，**WorkBuddy 里的 offline-ai MCP 工具现在启动即失败**（`local_llm_chat` 等全部不可用）。
- `agent.py` 用 `cfg["workspace_root"]`（旧路径）+ `bridge_dir` 构造 Bridge，`Bridge.__init__` 会 `mkdir(parents=True)` **在旧盘路径下凭空创建一套 `.offline-bridge` 目录**，然后永远等待不会到来的任务。用户往 `E:/Workbuddy/离线AI/.offline-bridge/inbox` 放的任务 JSON，agent 根本收不到。

**修复**：
```yaml
# config.yaml
workspace_root: "E:/Workbuddy/离线AI"
```
```json
// ~/.workbuddy/mcp.json
"args": ["E:/Workbuddy/离线AI/offline-ai/server/mcp_server.py"]
```
改完需在 WorkBuddy 连接器页面**重新信任** offline-ai MCP server 才会生效。

**根治建议**：启动脚本与 config 不应硬编码绝对路径。`start_agent.sh` 已用 `$(dirname "$0")` 推导，应让 `config.yaml` 支持 `workspace_root: auto`（取项目上级目录）或启动时用 `--workspace` 参数覆盖。

### BUG-2【P1】流式响应为空时「正在思考」气泡永久卡死

**位置**：`chat_app.py:950-965`

`_on_token` 只在收到非空 token 时才移除思考气泡；若模型返回空响应（或首 token 前连接被重置但没抛异常），`_finish()` 只把 `self.think_item = None`，**没有从布局移除 widget** → 界面上永远留一个"正在思考…"。

**修复**：`_finish()` 中补一句：
```python
def _finish(self):
    if self.think_item is not None:
        self._remove_item(self.think_item)
        self.think_item = None
    ...
```

## 2. 安全隐患

### SEC-1【高危 · 可远程代码执行】shell 白名单形同虚设

**位置**：`tools.py:58-70`

```python
base = cmd.strip().split()[0].lower()      # 只检查第一个词
if base not in self.shell_allowlist:
    return ...
subprocess.run(cmd, shell=True, ...)       # 但整条命令交给 shell 解释
```

**两道独立的绕过路径**：
1. **命令链注入**：`cat a.txt && python evil.py` → base = `cat`（在白名单）→ `shell=True` 会把 `&&` 后面的 `python evil.py` 一并执行。
2. **白名单自带后门**：`python` / `python3` 本身就在默认白名单里 —— `python -c "import os; os.system('任意命令')"` 直接通过检查，**不需要任何绕过技巧**。

**即使 `allow_shell: false` 是默认值**，这是一个"看起来安全"的陷阱配置：用户某天为了省事打开开关，就等于把工作区shell 交出去了。而 `write_file`（见 SEC-3）又能改 config 打开这个开关。

**修复**（二选一）：
- 彻底删除 `run_shell`（离线场景模型需要的文件操作已由 read/write/list 覆盖）；
- 或改为 `shell=False` + `shlex.split` + 从白名单中**移除 python/python3**，且只允许无管道无重定向的单命令。

### SEC-2【高危】`_safe()` 路径穿越（前缀匹配漏洞）

**位置**：`tools.py:24-28`

```python
p = (self.ws / path).resolve()
if not str(p).startswith(str(self.ws)):    # 前缀匹配，非路径分量匹配
```

经典绕过：workspace 为 `.../2026-10-11-17-27-15` 时，传入
`../2026-10-11-17-27-15-evil/secret.txt` → resolve 后为 `.../2026-10-11-17-27-15-evil/secret.txt`，`startswith` 返回 **True**，检查放行。同级目录的任何文件都可读。

**修复**（Python ≥3.9 可用 `is_relative_to`，本机 3.13/3.14 满足）：
```python
if not p.is_relative_to(self.ws):
    raise ValueError(f"path escapes workspace: {path}")
```

### SEC-3【中危】`write_file` 无任何限制，可覆盖配置文件形成组合攻击

**位置**：`tools.py:39-46`

可以写 workspace 内**任意路径、任意大小**内容。攻击链：
1. 模型（或被注入的 prompt）让 agent `write_file("offline-ai/config.yaml", ...)` 把 `allow_shell` 改为 `true`；
2. agent 重启后 SEC-1 生效 → RCE。

**修复**：写保护清单（config.yaml / *.json 配置 / mcp.json），单文件大小上限（如 1MB），可写目录白名单（如仅 `output/`、`notes/`）。

### SEC-4【中危】Prompt 注入 + 敏感文件无黑名单

**位置**：`agent.py:45-54`

agent 的 system prompt 明确声明"可读取用户工作区文件"，而 `handle_task` 对 `task.files` **没有数量限制、没有类型过滤、没有敏感文件黑名单**。inbox 里的任务 JSON 任何能写文件的人都能投放，其中 `files` 可指向 `.env`、`*.pem`、`.git/config`、`id_rsa` 等 —— 内容会连同 prompt 一起进入模型上下文，模型可能在回复中原样复述。

**修复**：敏感模式黑名单（`.env`、`*key*`、`*.pem`、`.git/`、`*secret*`）、`files` 数量上限（如 10）、总上下文字符上限（如 24000，见 PERF-3）。

### SEC-5【低危】MCP 工具无输入长度限制

`local_llm_chat(prompt)` 对 prompt 长度无上限。超长 prompt 在 CPU 上会把 prefill 拖到数分钟且占满内存（16GB 机器上 5GB 空闲），构成本地 DoS。建议 prompt 上限 32000 字符，超限直接报错而非截断。

### SEC-6【低危】便携 Ollama 无完整性校验

`chat_app.py` 从打包资源拷贝 `ollama.exe` 到 `%LOCALAPPDATA%` 后直接执行，无哈希校验。分发生态下这是供应链信任问题（当前单人使用低风险）。建议打包时记录 sha256，`_copy_ollama_to_persistent` 时校验。另：**切勿把 `OLLAMA_HOST` 设成 `0.0.0.0`** —— ollama 服务本身无鉴权，对外开放等于把本机模型控制权交出去。

## 3. 性能问题

### PERF-1【中危 · 已知坑未修完】agent/mcp 仍在用 localhost，每次请求白丢 ~2s

项目记忆里已记录"`localhost:11434` 会走 IPv6 回退导致每次请求 ~2s，代码里一律用 `127.0.0.1`"—— `chat_app.py:25` 确实改了，但：
- `mcp_server.py` 用 `ollama.generate()`，ollama 库默认连 `http://localhost:11434`；
- `agent.py` 同样。

**两处都漏改**。每次 MCP 调用 / 每个 agent 任务都固定多花约 2 秒 DNS+回退。

**修复**：两个文件在 import ollama 后加：
```python
os.environ.setdefault("OLLAMA_HOST", "127.0.0.1:11434")
```

### PERF-2【中危】模型未设 `keep_alive`，闲置 5 分钟即卸载，下次冷加载 15~180s

ollama 默认 `keep_alive=5m`。本机纯 CPU，qwen3:4b 热加载约 18s、**冷加载偶发 >180s**。MCP server 是长驻进程，两次调用间隔稍长就触发卸载→重载，用户体验上就是"第一次问卡 3 分钟"。

**修复**：所有调用加 `options={"keep_alive": -1}`（常驻内存）或至少 `"30m"`。注意与 16GB 内存权衡：常驻 4B 模型约占 3GB，可接受；7B（config 当前默认值，约 4.7GB）常驻有风险，见 PERF-7。

### PERF-3【中危】`num_ctx` 未设置 + 长文本静默截断

ollama 默认 `num_ctx=2048`。
- `local_llm_summarize` 截 `text[:12000]` **字符** ≈ 6000~12000 token，**必超 2048 被静默截断**，摘要质量随机受损，用户无从得知；
- agent 侧 `files` 无上限，一个 50 文件的任务就是 400KB prompt，CPU prefill（O(n²) attention）可能跑几十分钟。

**修复**：显式 `num_ctx=4096`（4B 模型 CPU 上 4096 prefill 约 30~60s，可接受）；摘要输入截到 4000 字符；agent 限制 `len(task.files) ≤ 10` 且拼接后总长 ≤ 24000 字符，超限在 result 里明确报错。

### PERF-4【中危】agent 串行处理 + 3 秒轮询，无队列无取消

`agent.py:66-82`：单线程 for 循环逐个处理，一个大任务（CPU 3.8 tok/s 生成 2000 字 ≈ 8 分钟）阻塞后面所有任务；轮询每 3 秒全量 glob + 读所有 JSON。

**修复**：轮询改 `watchdog` 文件事件（或轮询间隔改 1s 但只 `stat` 不读内容）；加任务队列（`collections.deque` + 状态文件），至少做到：排队可见（outbox 写 queued 状态）、支持写 `cancel` 标记文件中断（Ollama 生成中关闭 HTTP 连接即中断）。

### PERF-5【中危】流式渲染每 token 全量重排

`chat_app.py:296-297, 950-958`：每个 token 触发一次 `token.emit(buf)` → `_on_token` → `set_text(buf)` 全量 HTML 重建 + wordWrap 重排 + `QTimer.singleShot(0)` 滚底。一次 2000 字回答 ≈ 1500 次全量重渲染 + 1500 个定时器入队，长回答后段明显掉帧。

**修复**：节流到 ~10fps（`QElapsedTimer` 或 100ms 合并窗口）；滚底用「用户未手动上滚才自动滚」判断 + 节流。

### PERF-6【低危】`Worker` 120s socket 超时偏紧

`chat_app.py:284` `timeout=120`：CPU 上 8B 模型冷加载 + 长 prompt prefill，首 token 可能 >120s（项目记录 qwen3:4b 冷加载偶发 >180s），会被误判为连接失败。

**修复**：连接超时 10s、读取超时 600s（需拆成两次设置或接受整个生成期一个长超时）。

### PERF-7【低危】config 默认模型选错

`config.yaml:3` 默认 `qwen2.5:7b`，但本机实测结论是「16GB 内存空闲仅 ~5GB，只适合 ≤4B；7B 勉强需先腾内存」。MCP/agent 用 7B 默认值 = 默认处于内存压力+3.8 tok/s 慢速档。

**修复**：默认改 `qwen3:4b`（或按 PERF-8 路由）。

### PERF-8【低危】9 个内置模型串行 `ollama create`

`chat_app.py:211-251`：首次导入 14GB 模型时串行执行 9 次 create，每次含 blob 校验/拷贝。磁盘 IO 是瓶颈，并行 2~3 个能缩短总时长（CPU 校验会竞争，收益有限，优先级低）。

## 4. 可靠性问题

### REL-1【中危】坏任务 JSON 静默丢失

`protocol.py:77-78`：`list_pending` 的 `except Exception: continue` 会把缺字段、JSON 语法错误的任务**无声跳过**，用户以为已提交，实际永远不执行，且无任何记录。

**修复**：解析失败时 `bridge.log(...)` 记录文件名与原因，或把坏文件移到 `.offline-bridge/inbox/.bad/`。

### REL-2【中危】非原子写入，崩溃留半个 JSON

`protocol.py:83, 87` 直接 `write_text`。写入中途断电/崩溃 → 半个 JSON 文件，虽会被跳过（见 REL-1），但 **outbox 损坏 = 用户丢结果**。

**修复**：原子写范式：
```python
tmp = out.with_suffix(".tmp")
tmp.write_text(...)
tmp.replace(out)   # 同分区 rename 原子
```

### REL-3【中危】agent 崩溃后 running 任务成"死任务"

`agent.py:68-81`：`mark_running` 后若进程被杀（断电/手动结束），inbox 里该任务状态永远停在 `running`，`list_pending` 只收 `pending` → 永不重试、永不报错。

**修复**：agent 启动时把 inbox 中 `status == "running"` 的一律重置为 `pending`（简单可靠）；或记录心跳时间戳，超时（如 30 分钟无更新）自动重置。

### REL-4【低危】`task_id` 碰撞互相覆盖

`protocol.py:86`：outbox 文件名 = `task_id.json`。两个任务用同一 ID（如都叫 "t1"）→ 后者覆盖前者结果。

**修复**：落盘时 ID 加时间戳后缀，或接收时查重拒绝。

## 6. AI 全能性提升（10 项）

### AIV-1【最大缺口】agent 有工具集却不会用 —— 从"复读机"变"智能体"

`agent.py:45-54`：`Tools` 类实现了 `read_file / write_file / list_dir / run_shell` 四件套，`handle_task` 却**只调用了 `read_file`**，然后把所有内容塞进一个 prompt 让模型一次性回答。这意味着：
- 模型看不到目录结构，不知道有哪些文件可用；
- 无法写文件产出、无法列目录探索、无法多步推理（读 A → 发现要读 B → 再读 B）。

**修复路径**（两阶段）：
1. **短期**：文本 ReAct 协议。在 prompt 中约定 `Thought:/Action:/Action Input:` 格式，agent 解析 Action 调用 Tools，把 Observation 追加回上下文，循环直到 `Final Answer`。小模型（≤4B）对格式遵循弱，需 few-shot 示例 + 最多 5 轮限制。
2. **中期**：Ollama 原生 tool calling。ollama ≥0.5 的 `/api/chat` 支持 `tools=[...]` 参数（qwen2.5 / qwen3 / gemma3 均支持），把四个 Tools 方法注册为 JSON schema function，模型自主决定调用，比文本协议可靠得多。`requirements.txt` 的 `ollama>=0.4.0` 需提高到 `>=0.5`。

### AIV-2【高价值】MCP 工具集扩充（现仅 3 个 chat 变体）

`mcp_server.py:40-59` 三个工具本质是同一功能的温度参数变体。建议新增：

| 新工具 | 用途 | 依赖 |
|---|---|---|
| `local_llm_embed` | 文本向量化，支撑语义搜索/RAG（见 AIV-4） | ollama embeddings API |
| `local_llm_vision` | 图像理解（gemma3:1b/4b 是多模态模型，已装却完全没用上） | 图片→base64 |
| `local_model_list` | 列出本机可用模型+体积，让调用方知道有什么弹药 | /api/tags |
| `local_llm_code` | 代码任务路由到 `qwen2.5-coder:3b`（已装未用） | 模型路由 |
| `local_llm_translate` | 专用翻译（低温、模板化） | 提示词模板 |
| `local_agent_task` | 直接向 bridge inbox 投递任务并查询结果，把文件桥能力也 MCP 化 | bridge/protocol.py |

### AIV-3【高价值】模型路由：按任务选模型，别用一个 7B 打天下

本机已装 11 个模型，目前 `config.yaml` 写死一个。建议路由表：

| 任务类型 | 推荐模型 | 理由 |
|---|---|---|
| 分类/抽取/简单问答 | qwen3:0.6b | 1GB 内存，最快 |
| 摘要/翻译 | qwen3:1.7b | 速度质量平衡 |
| 通用对话/写作 | qwen3:4b | 当前硬件甜点 |
| 代码生成/解释 | qwen2.5-coder:3b | 专用 coder |
| 数学/推理链 | deepseek-r1:1.5b | R1 蒸馏 |
| 图像理解 | gemma3:4b | 唯一多模态 |

### AIV-4【高价值】本地 RAG：让离线 AI 拥有你的领域知识

小模型通用知识弱，但你的真实需求是**基于自己的论文库/项目文档问答**。方案：
- `ollama.embeddings(model="qwen3:0.6b", ...)` 生成向量（或 `nomic-embed-text`，约 274MB，值得装）；
- 存 `sqlite-vec`（零依赖扩展）或纯 numpy + JSON；
- 切分 workspace 的 docs/ 与论文 PDF（`pdf` skill 已有能力）；
- 暴露 `local_rag_query(question)` MCP 工具：检索 top-k → 拼上下文 → 生成。

对 RFS-DRL 项目（论文库 + 代码库）立即可用，且完全离线。

### AIV-5 流式 MCP 响应

`mcp_server.py` 是非流式，WorkBuddy 侧调用一个长生成任务时干等。FastMCP 支持 yield 流式返回，可把生成进度/增量推给调用方（实现复杂度中等，优先级中）。

### AIV-6 agent 上下文记忆

### 9.2 新发现：Ollama 侧模型行为缺陷（本次实测确证）

1. **`qwen3:4b` + `num_ctx=4096` → 输出乱码**（`,,,,,` / `0000` / 多语言 token 沙拉），
   而 2048/3072/6144/8192 全部正常 → Ollama 该模型上下文分桶的特定缺陷；
   agent 冒烟时的 `token repeat limit reached (500)` 即此问题的表现。
   **规避：统一 `num_ctx: 6144`，永远不要给 qwen3:4b 设 4096。**
2. **`qwen3` 系默认 thinking 模式**：`/api/chat` 的 `content` 恒为空（内容全在 `thinking`），
   `/api/generate` 混入 `<think></think>` 块，短任务还会因思考循环触发 repeat-limit 中止。
   **规避：qwen3 自动加 `/no_think` 前缀 + 正则清理 `<think>` 块 + UI 空内容回退展示 thinking。**
